# 사전 점검 (셀프 게이트)

원고를 리뷰어에게 넘기기 전에 여섯 기준으로 점수를 매기고, 통과 조건에 못 미치면 저자 쪽에서 먼저 수정한다. 구조 검사(5단계)를 통과한 원고에 실행하고, 결과는 작업 폴더의 `gate-report.md`에 남긴다. 이미 있는 Markdown 원고를 받아 점검만 해 달라는 요청에도 같은 절차를 따른다. (2026-11-25 추가. 기준과 리포트 형식은 github.com/comeddy/blog-precheck-plugin의 `gate.md`를 따랐고, 측정 방법만 이 skill의 스크립트에 맞췄다)

## 통과 조건

- 총점(여섯 점수의 평균, 소수점 아래 버림)이 70 이상
- 모든 기준이 최저선 이상. 총점이 높아도 한 기준이 최저선에 못 미치면 반려다
- 채점은 두 회차까지다. 1회차가 반려면 미달 기준만 수정해 2회차를 채점한다. 2회차에도 미달이면 판정을 "2회 초과 전달"로 적고, 미달 기준을 리포트에 남긴 채 넘긴다. 점수를 올리려고 글을 밋밋하게 만드는 것보다 리뷰어의 판단이 낫다

## 기준 여섯 개

|---|---|---|---|
| 1 | 정합성 | 100점에서 불일치 1건마다 10점을 뺀다. 아래 "정합성에서 보는 것" 다섯 가지 | 80 |
| 2 | 구조 완결성 | 일곱 항목 가운데 충족한 비율에 100을 곱한다(소수점 아래 버림): 도입(문제 제기), 솔루션 개요, 실전 단계, 결과 증거(캡처나 수치), 리소스 정리, 비용 언급, 다음 단계와 CTA | 70 |
| 3 | 표기 규범 | 100점에서 위반 1건마다 10점을 뺀다. 같은 표현이 여러 번 나와도 1건이다. 아래 "표기 규범에서 보는 것" 여섯 가지 | 70 |
| 4 | 중복과 군더더기 | `redundancy_metrics.py --restated <건수>`가 출력한 기준 4 점수 | 60 |

| 6 | 가독성 | 비문 0건(40), 번역투 3건 이하(30), 모든 문단이 5문장 이하(30). 항목마다 충족하면 배점 전부, 아니면 0점이다 | 60 |

### 정합성에서 보는 것

1. `check_structure.py`가 통과한다. 그림과 표 번호가 등장 순서와 맞고, 캡션이 아래에 있고, 이미지 파일이 있다
2. `check_urls.py`가 모든 링크를 `OK`로 판정한다. `FAIL`과 `REDIRECT`는 1건씩 센다. `REDIRECT`는 verification.md대로 최종 URL이 맞는 문서이면 그 URL로 바꾸고(한국어 페이지로 넘어가는 경우 포함), 링크 제목도 그 페이지의 실제 제목으로 맞춘다
3. 본문에 적은 수치가 표, 그림, 코드의 수치와 같다. 비율과 합계는 Python으로 다시 계산한다(verification.md의 수치 검산)
4. 본문에 적은 메서드, 클래스, 파라미터, 리소스 이름이 같은 문단의 예시 코드와 실행 결과에 그대로 있다. 설명은 `isEmpty`인데 마지막 문장만 `isBlank`로 적은 경우가 여기에 걸린다
5. 아키텍처 흐름 번호를 가리키는 문장이 흐름 목록의 실제 항목과 맞다. "6번(토큰 검증)"이라고 썼는데 목록의 6번이 "도구 조회"면 불일치다

코드 블록도 여기서 함께 본다. 모델 ID와 API 파라미터 이름은 공식 API 문서와 대조하고, 언어 라벨이 내용과 맞는지(Python 코드에 `javascript` 라벨), 예시 스타일이 글 전체에서 같은지(bash CLI와 JSON 조각을 섞지 않음), 예시 도메인이 RFC 2606 계열인지, 출력에 계정 ID나 시크릿이 남지 않았는지 확인한다. 어긋난 곳은 1건씩 센다.

세는 단위는 문장, 코드 블록, 표의 칸 하나다. 한 문장에 틀린 곳이 둘이어도 1건이고, 언어 라벨이 없는 코드 블록도 1건이다.

### 표기 규범에서 보는 것

1. `lint_prose.py`의 HARD 항목이 0건이다
2. 서비스 이름이 첫 등장에서 Amazon이나 AWS 접두사를 붙인 정식 이름이다
3. AWS 한국어 공식 문서의 용어를 쓴다(예: "공인 인증서"가 아니라 "퍼블릭 인증서")
4. 같은 대상을 두 가지로 적지 않는다. 전수 검색으로 확인한다(예: 컨텐츠와 콘텐츠, 워크플로와 워크플로우, Runtime과 AgentCore Runtime). 이름이 비슷한 다른 리소스(AgentCore Gateway, Internet Gateway)는 통일 대상이 아니다
5. 용어 3층위(발표 기능명, 문서 페이지명, API 파라미터명)를 구분했다(verification.md)
6. 섹션 번호 참조가 없다(SKILL.md 3단계의 grep)

### 차별성과 근거, 가독성에서 보는 것

- 같은 주제의 글을 WebSearch로 3개 이상 찾아 URL과 이 글이 다른 점을 한 줄씩 적는다. AWS 공식 블로그, 벤더 블로그, 커뮤니티 글을 합쳐 3개면 된다. 검색 결과만으로 다른 점을 적을 수 없으면 WebFetch로 읽는다. 이미 공식 기능이나 문서로 나온 내용을 놓쳤는지도 이때 확인한다
- 차별점 문장은 이 글이 다른 글과 무엇이 다른지 독자가 알 수 있는 본문 문장이다. 글의 범위만 소개하는 문장("이 글에서는 전환 절차를 정리합니다")은 차별점이 아니다
- 비문은 주어와 서술어, 목적어와 동사의 호응이 어긋난 문장이다(예: "좌표를 줄 뿐 길을 주지 못합니다"는 "길을 알려주지 못합니다")
- 번역투 건수는 `lint_prose.py` 출력에서 `[!]`가 붙은 A 분류 줄의 수다(임계를 넘은 번역투 패턴 수): `python3 "${CLAUDE_SKILL_DIR}/scripts/lint_prose.py" <md> | grep -c '\[!\].* A-[0-9]'`. `my-plugins:kor-deslop` 점검만 모드의 지적은 수정안을 쓸 때 참고하고 건수에는 넣지 않는다

## 채점 원칙

- 스크립트가 재는 항목은 출력값을 그대로 쓴다. 정합성의 1과 2, 표기 규범의 1, 가독성의 번역투 건수, 기준 4 전체가 여기에 든다. 짐작으로 매기지 않는다
- 읽어서 세는 항목(정합성의 3~5와 코드 블록, 표기 규범의 2~6)은 전수 검색과 대조로 찾고, 1건마다 원문을 인용한다
- 2, 5, 6번은 판단이 들어가므로 근거가 된 원고 문장을 인용해 점수를 적는다. 근거 없는 점수는 무효다
- 깎인 점수에는 모두 감점 사유를 "원문 인용, 수정안" 쌍으로 남긴다. 원고에 없어서 깎인 내용(리소스 정리, 차별점 문장)은 넣을 자리 바로 앞 문장을 인용하고 수정안에 넣을 문장을 쓴다
- "의도적으로 유지: <이유>"는 사용자가 수정하지 않겠다고 한 감점 사유에만 수정안 뒤에 붙인다. 통과한 기준에 남은 감점 사유에는 표시가 필요 없다

## 중복과 군더더기 지표

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/redundancy_metrics.py" "$W/drafts/<slug>.md" --restated <재진술 건수>
```

같은 문단의 반복, 같거나 비슷한 문장의 반복(한글 공통 구절 20자), 메타 강조 문장("핵심", "중요한 점은"), 따옴표 조어 밀도, 6문장 이상 문단, 상투어 밀도를 잰다. 표, 코드, 캡션, 참고 자료, 저자 소개는 재지 않는다. AI가 썼는지가 아니라 읽기에 방해되는지만 본다.

같은 뜻을 다른 문장으로 되풀이하는 재진술은 스크립트가 잡지 못한다. 섹션마다 핵심 메시지를 한 줄씩 적어 겹치는 것을 세고 그 수를 `--restated`에 넘긴다. 없으면 `--restated 0`이다. 1건마다 5점이 빠진다. 출력 전체를 리포트의 "지표 원본"에 붙인다.

스크립트가 이미 반복 문장이나 유사 문장으로 잡은 것은 재진술로 다시 세지 않는다. 마치며가 리드의 질문에 답하며 본문의 결론을 한 번 정리하는 것도 재진술이 아니다(structure.md의 수미상관). 같은 주장이 본문의 서로 다른 섹션에 다시 나오거나 마치며가 같은 결론을 두 번 이상 말할 때 센다.

구호처럼 쓴 불릿, 섹션 구조가 같은 것, 문장 길이의 분산, 과거형 비율은 재지 않는다. AI 티를 찾을 때는 쓰지만 독자가 읽는 데는 방해되지 않는다. 따라 하는 글은 섹션 구조가 같아야 따라 하기 쉽다.

## gate-report.md 형식

작업 폴더 루트(`$W/gate-report.md`)에 저장한다. 표의 기준 이름과 순서, 판정 낱말(통과, 미달, 반려, 2회 초과 전달)은 그대로 쓴다.

```markdown
# Gate Report: <블로그 제목>
회차: 1 / 2 | 판정: 반려

| 기준 | 점수 | 최저선 | 판정 |
|---|---|---|---|
| 정합성 | 100 | 80 | 통과 |
| 구조 완결성 | 100 | 70 | 통과 |
| 표기 규범 | 90 | 70 | 통과 |
| 중복과 군더더기 | 55 | 60 | 미달 |
| 차별성과 근거 | 100 | 60 | 통과 |
| 가독성 | 100 | 60 | 통과 |
| **총점** | 90 | 70 | **반려 (중복과 군더더기 미달)** |

## 채점 근거
### 구조 완결성
> (항목을 충족한다고 본 원고 문장)

여섯 항목 모두 충족. 리소스 정리는 해당 없음(독자가 리소스를 만들지 않는 비용 분석 글).
### 차별성과 근거
> (차별점을 적은 원고 문장)

비교한 글과 이 글이 다른 점:
- https://example.com/post-1 다른 점 한 줄
- https://example.com/post-2 다른 점 한 줄
- https://example.com/post-3 다른 점 한 줄
### 가독성
> (판단의 근거가 된 원고 문장)

비문 0건, 번역투 2건, 가장 긴 문단 4문장.

## 감점 사유 (원문 인용 → 수정안)
### 표기 규범 (90)
> (원문)

→ (수정안). 이유: (한 줄 근거)
### 중복과 군더더기 (55)
> (원문)

→ (수정안). 이유: (한 줄 근거)

## 중복과 군더더기 지표 원본
## 중복과 군더더기 지표: <slug>.md

**점수: 60/100** (높을수록 읽기에 방해되는 요소가 적음, 최저선 60)

| 지표 | 측정값 | 기준 | 감점 |
|---|---|---|---|
| 보일러플레이트 문단 반복 | 1회 | 0 | -6 |
| 문장 반복 (동일 또는 한글 공통 구절 20자) | 동일 0, 유사 2 | 0 | -16 |
| 메타 강조 문장 | 3회 | ≤ 1 | -10 |
| 따옴표 조어 밀도 (1000자당) | 1.7 (5회) | ≤ 1.0 | -3 |
| 6문장 이상 문단 | 1개 | 0 | -5 |
| 상투어 밀도 (1000자당) | 1.0 (3회) | ≤ 1.5 | -0 |

재진술 1건: -5

**기준 4 점수: 55/100**
```

100점이 아닌 기준은 모두 `### <기준> (<점수>)` 제목으로 감점 사유를 적고, 제목의 점수는 점수표와 같게 쓴다. 인용은 `>`로 시작하는 줄에, 수정안은 `→`로 시작하는 다음 줄에 쓴다. 한 줄에 함께 쓰면 검사가 쌍으로 읽지 못한다. 지표 원본에는 스크립트 출력을 줄이지 않고 그대로 붙인다.

2회차 리포트를 쓰기 전에 1회차 리포트를 `$W/gate-report-round1.md`로 남긴다. 2회차 리포트는 회차 줄 아래에 `이전 회차: 1회차 총점 90, 중복과 군더더기 55 미달` 한 줄을 적고, 감점 사유에는 수정한 뒤에도 남은 것만 적는다. 수정한 내용은 `## 2회차에 수정한 것` 섹션에 원문과 바꾼 문장을 한 쌍씩 적어 지표 원본 앞에 둔다.

리포트를 쓴 뒤 검사한다. 총점과 판정을 점수에서 다시 계산해 리포트와 다르면 실패한다.

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/check_gate.py" "$W/gate-report.md"
```

종료 코드 0은 넘겨도 되는 리포트(통과, 또는 2회차의 2회 초과 전달), 3은 반려, 1은 리포트가 빠졌거나 점수와 판정이 맞지 않음이다. 채점 규칙으로 나올 수 없는 점수(정합성 95, 가독성 65), 비교한 글의 URL이 3개보다 적은 차별성과 근거, 감점 표와 맞지 않는 지표 점수도 1이다.

`package_blog.sh`는 같은 검사를 `--draft <번들의 원고>`와 함께 실행한다. 이때 지표를 원고에서 다시 재어 리포트의 지표 원본과 비교하므로, 다른 원고의 리포트이거나 채점한 뒤에 원고가 바뀌어 지표가 달라졌으면 zip이 만들어지지 않는다. 원고를 수정했으면 `redundancy_metrics.py`를 다시 실행해 기준 4와 지표 원본을 새 출력으로 바꾼다.

## 수정과 재채점

1. 채점하고 `gate-report.md`를 저장한다
2. 반려면 미달 기준의 감점 사유만 수정한다. 모든 기준이 최저선을 넘었는데 총점만 70에 못 미치면 점수가 가장 낮은 기준부터 수정한다. 통과한 기준은 건드리지 않는다. 다시 손대면 새 오류가 생긴다
3. 미달 기준만 다시 채점하고 회차를 2로 올려 리포트를 갱신한다. 원고를 수정했으므로 스크립트는 모두 다시 실행한다(`check_structure.py`, `lint_prose.py`, `check_urls.py`, `redundancy_metrics.py`). 스크립트 값이 달라진 기준은 통과한 기준이어도 새 값으로 적고, 판단으로 매긴 기준 가운데 통과한 것은 다시 매기지 않는다
4. 통과했거나 2회차를 마쳤으면 패키징으로 넘어간다

## 채점 뒤에 원고를 교정했을 때

게이트를 통과한 뒤 사용자의 요청으로 원고를 교정하면 다음 순서를 따른다.

1. `check_structure.py`, `lint_prose.py`, `redundancy_metrics.py`를 다시 실행하고, 링크를 바꿨으면 `check_urls.py`도 실행한다
2. 스크립트 값이 달라진 기준은 리포트를 새 값으로 갱신한다. 회차는 올리지 않는다. 리포트가 교정 전 문장을 인용한 곳은 새 문장으로 바꾸고, 교정 내용을 `## 채점 뒤 교정` 섹션에 원문과 교정문 한 쌍으로 적어 지표 원본 앞에 둔다
3. 갱신한 결과 어떤 기준이 최저선 아래로 내려가면 요청받지 않은 문장을 묻지 않고 수정하지 않는다. 원인(어느 문장이 어느 문장과 겹치는지)과 수정안, 수정안을 적용했을 때의 점수를 점수표와 함께 제시하고 사용자의 선택을 받는다
4. 1회차 리포트였으면 판정이 반려가 되어 zip이 만들어지지 않으므로 이 사실도 함께 알린다. 사용자가 수정안을 고르면 적용해 2회차로 채점한다. 그대로 넘기겠다고 하면 회차를 2로 올려 "2회 초과 전달"로 적고 그 감점 사유에 "의도적으로 유지"를 붙인다. 2회차 리포트였으면 판정이 "2회 초과 전달"로 바뀌고 zip은 만들어진다

## 점수 제시 (2026-11-25 확정)

원고를 작성한 세션은 사용자가 묻지 않아도 점수를 제시한다.

- 채점할 때마다(1회차, 2회차) `check_gate.py`가 출력한 점수표를 사용자에게 보여 준다
- 마지막 응답에는 `package_blog.sh`가 끝에 출력한 `scores:` 점수표를 그대로 넣는다. 여섯 기준의 점수, 최저선, 판정과 총점이 한 표에 있다
- 표 아래에 100점이 아닌 기준마다 감점 사유를 한 줄씩 적는다. "의도적으로 유지"로 둔 항목과 2회차에도 미달인 기준은 따로 밝힌다
- 2회차로 끝났으면 1회차 총점과 수정한 내용을 한 줄로 덧붙인다
- 원고를 수정해 zip을 다시 만들 때마다 같은 방식으로 다시 제시한다
- 사용자가 사전 점검을 빼 달라고 해서 `--no-gate`로 패키징했으면 점수 대신 사전 점검을 하지 않았다고 적는다

## 리뷰어에게 남기는 것

게이트를 통과한 원고의 리뷰어는 오타, 정합성, 문체를 다시 보지 않고 기술적 정확성(서비스 동작이 실제와 맞는가)과 고객 관점(이 글을 받은 고객이 바로 쓸 수 있는가)에 집중한다. 그래서 `gate-report.md`를 번들에 함께 넣는다. 리뷰어가 추가로 판단할 것은 "의도적으로 유지"로 표시한 감점 사유와 2회차에도 미달인 기준이다.
