# 게시 준비: WordPress 변환본과 게시 후 공지 문구

원고를 리뷰어에게 넘길 때 WordPress 코드 편집기에 붙여넣을 변환본을 함께 주고, 게시가 끝나면 공지 문구를 쓴다. (2026-11-25 추가. 변환 규칙과 공지 문구의 형식은 github.com/comeddy/blog-precheck-plugin의 blog-precheck skill을 따랐다)

## WordPress 변환본 (wordpress.md)

`package_blog.sh`가 번들의 원고를 변환해 `out/<slug>/wordpress.md`로 넣는다. 변환만 따로 할 때는 다음과 같이 실행한다.

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/md_to_wordpress.py" "$W/drafts/<slug>.md" --out "$W/wordpress.md"
```

WordPress에는 아무것도 올리지 않는다. 이미지 `src`는 `images/<파일명>` 로컬 경로로 두고, 미디어 라이브러리 업로드와 URL 치환은 리뷰어가 한다. 변환본은 직접 수정하지 않고 원고를 수정한 뒤 다시 변환한다. 변환본에만 필요한 HTML(동영상 태그, 표 너비)은 마지막에 한 번 넣고 그 내용을 사용자에게 알린다.

### 변환 규칙

| 원고 | 변환본 |
|---|---|
| 프론트매터, H1 제목, 바이라인 | 본문에서 빼고 맨 위 HTML 주석에 제목, 추천 URL slug, 예상 URL, 카테고리를 적는다. 제목은 WordPress 제목 필드에, slug는 고유주소에 넣는다. 주석이라 통째로 붙여넣어도 화면에 보이지 않는다 |
| `## 1. ...`, `### 1.1 ...` | `<h2>`, `<h3>`. 본문은 `<h2>`부터 시작한다 |
| 구분선(`---`) | 제거한다. 테마가 구분선을 가운데 정렬된 짧은 선으로 그리고, 섹션은 h2 제목이 구분한다 |
| 이미지 | `<p style="text-align: center;"><img src="images/<파일명>" alt="..." /></p>`. base64 데이터 URI, `images/` 밖의 경로, 공백이나 특수문자가 든 파일 이름은 변환을 멈춘다 |
| 표 | 실제 HTML 표. 테마의 기본 표는 테두리가 회색이거나 없으므로 인라인 스타일로 검은 테두리, 가운데 배치, 아래 여백 8px을 주고, 머리 행은 `<thead>`와 `<th>`에 연회색 배경(`#f2f3f3`)을 준다. 정렬 표시(`:---:`, `---:`)는 `text-align`으로 옮긴다 |
| 표와 그림 캡션 | 바로 아래 가운데 정렬: `<p style="text-align: center; margin-top: 0;"><em>표 N. ...</em></p>` |
| 코드 블록 | `<pre><code class="lang-<언어>">`. 펜스의 언어 라벨(첫 낱말)을 그대로 옮긴다. 라벨이 없으면 `lang-text`로 두고 알린다 |
| 인라인 코드, 링크, 굵은 글씨, 기울임 | `<code>`, 문장 안의 `<a href>`, `<strong>`, `<em>`. 링크 URL은 `http`, `https`, `mailto`, 상대 경로만 받고 그 밖의 스킴(`javascript:` 등)은 변환을 멈춘다 |
| 목록 | `<ul>`, `<ol>`. 항목에 딸린 코드 블록과 하위 목록은 `<li>` 안에 넣는다 |
| 원고에 직접 적은 HTML 태그 | 글자로 바꿔 넣는다(`<br>`만 그대로). 소재에서 옮겨 온 글자가 페이지의 마크업이 되지 않게 하기 위해서다. 태그가 필요하면 변환본에 직접 적는다 |

### 추천 URL slug

프론트매터에 `slug: <english-slug>`를 적는다. 제목의 핵심어를 영어로 옮겨 소문자와 하이픈으로 쓰고, 서비스 이름은 공식 영문 표기를 따르며, "방법과 활용 사례" 같은 꼬리말은 길면 뺀다. `slug:`가 없으면 스크립트가 파일 이름에서 날짜를 뺀 값을 쓰고, 주석과 `[!]` 줄로 그 사실을 알린다. 이 값에는 제목의 핵심어가 빠지기 쉬우므로 `slug:`를 적고 다시 변환한다. 프론트매터는 본문이 아니므로 사전 점검이나 문장 교정만 요청받은 원고에도 `slug:`는 넣고 그 사실을 알린다. 예상 URL은 `https://aws.amazon.com/ko/blogs/tech/<slug>/`이고, 다른 채널이면 `--channel korea`를 준다.

### 스크립트가 알리는 것

- `[변환]`은 변환하면서 바꾼 것이다(제목과 바이라인을 주석으로, 구분선 제거). 마지막 응답의 "변환 시 바꾼 것"에 옮겨 적는다
- `[!]`는 확인이 필요한 것이다. 언어 라벨 없는 코드 블록은 내용을 보고 원고의 펜스에 언어를 적는다(계산식은 `text`). 꺾쇠로 감싼 URL(`<https://...>`)은 협업 도구에 붙여넣다 생긴 것인지 확인한다(collaboration.md)
- `[FAIL]`이 있으면 변환본을 쓰지 않고 종료 코드 1로 끝난다. 원고의 코드 블록, 표, 이미지, 캡션 수를 다시 세어 변환본과 다르면 이것도 실패다. 이 경우 변환기가 읽지 못한 문법이 있는 것이므로 원고의 그 부분을 이 skill의 골격(structure.md)에 맞게 바꾼다

### 변환 뒤 눈으로 확인할 것

- 표를 스크린샷 이미지로 넣지 않았는가. 이미지로 된 표는 검색되지 않고 확대하면 흐려지므로 내용을 읽어 원고의 Markdown 표로 다시 쓴다
- 열이 적어 좁아 보이는 표는 변환본의 `<table>` 스타일에 `width: 70%;`를 더한다
- 화면 캡처처럼 이 skill이 만들지 않은 이미지는 파일 이름에 공백이 없는지 본다. macOS 스크린샷 이름에는 눈에 보이지 않는 특수 공백(U+202F)이 들어간다
- 동영상은 링크(`<a href="...mov">`)로 넣으면 글자로만 보인다. 변환본에 `<video src="..." controls playsinline preload="metadata" width="642" style="max-width: 100%; height: auto;"></video>`를 넣고, 코덱이 H.264인지 확인한다(`ffprobe -select_streams v:0 -show_entries stream=codec_name <파일>`). HEVC는 Chrome에서 재생되지 않으므로 H.264 mp4로 다시 만든다
- 리뷰어가 이미지를 올린 뒤의 URL에 `-300x169` 같은 축소본 접미사가 붙으면 원본 URL로 바꿔야 선명하다. 이 내용은 리뷰어에게 전달할 항목에 적는다

### 리뷰어에게 넘길 때

zip 하나에 원고(`<slug>.md`), `images/`, `wordpress.md`, `gate-report.md`가 들어 있다. 리뷰어는 `images/`를 그대로 올리고, `wordpress.md`를 코드 편집기(HTML 모드)에 붙여넣은 뒤 이미지 `src`를 바꾼다. 비주얼 모드에 붙여넣으면 태그가 글자로 보인다.

## 게시 후 공지 문구

사용자가 게시가 끝났다고 알리거나 "공지 문구", "publish 문구", "슬랙 문구"를 요청하면 사내 채널에 올릴 문구를 쓴다. 문구만 쓰고 어디에도 보내지 않는다.

### 순서

1. 번들의 원고를 읽고 문제 제기, 접근 방법, 실전 내용을 파악한다
2. 문구를 쓰기 전에 사용자에게 묻는다. 빈칸을 남긴 초안을 먼저 만들지 않는다
   - 누가 올리는가: 저자 본인인지, 다른 사람의 글을 소개하는지
   - 저자 정보: 팀이나 직함, 이름, 채널에서 쓰는 핸들. 공동 저자가 있으면 모두
   - 게시된 글의 URL
3. 답을 받으면 빈칸 없이 바로 붙여넣을 수 있는 완성본을 한 번에 준다

### 문구 구조

두 문단, 전체 3~4문장으로 짧게 쓴다.

1. 인사, 저자 소개, 글 제목(게시 URL 링크), "게시되었습니다"
2. 문제의식과 접근 방법을 한 문장으로, 이어서 실전 내용과 추천 대상을 잇는 마무리 문장, 마지막에 감사 인사

감사 인사는 올리는 사람에 따라 다르다. 다른 사람의 글을 소개하면 저자에게("OO님, OO님 좋은 글 포스팅 감사드립니다!"), 저자 본인이 올리면 공동 저자와 리뷰어에게 돌린다.

마무리 문장은 같은 채널에 되풀이해 올라가므로 한 가지 틀로 굳히지 않고, 글의 차별점에 맞춰 아래 유형을 돌아가며 쓴다.

| 유형 | 예 |
|---|---|
| 고객 미팅의 근거 자료 | "~를 검토하는 고객 미팅에서 근거 자료로 활용하기 좋습니다" |
| 문서의 빈 곳 보완 | "공식 문서가 답하지 않는 ~를 측정값으로 채워 검증 시간을 줄여 주는 글입니다" |
| 문의 대응 | "~ 문의를 받았을 때 이 글 하나로 답변이 정리될 만큼 흐름이 명확합니다" |
| 대상 고객 구체화 | "~가 필수인 OO 업종 고객과 대화할 때 참고 자료가 될 글입니다" |
| 독자 질문에 답 | "'문서에는 없는데 실제로는 어떤가'라는 질문에 수치로 답하는 글입니다" |
